# Apollo «168 в 1 ТАНК»: практическая карта новых источников

**Дата проверки:** 16 октября 2026 года.  
**Целевой проект:** [grayhex/CrocodileMario][C-Repo].  
**Новые источники:** [brick.game/ru][B-Site] и [vitalibo/Brick-Game-9999-in-1][V-Repo].  
**Назначение:** руководство разработчику или coding-агенту: какие правила уже можно изучить, какие файлы читать, чего не копировать автоматически и как подключить игры к существующей оболочке.

> Это исследование двух современных реализаций, а не найденная прошивка Apollo. Описанные ниже правила vitalibo подтверждены чтением исходников, но не проверкой их совпадения с оригинальной игрушкой.

## 1. Решение по источникам

| Источник | Практическая ценность | Ограничение | Рекомендация |
|---|---|---|---|
| **brick.game** | Каталог игр и потенциальный браузерный стенд для сравнения поведения | Проверены публичная страница и условия использования; игровой JavaScript и поведение запущенных игр в этой сессии не исследованы | Вторичный референс; не спецификация Apollo и пока не подтверждённый донор кода |
| **vitalibo** | Компактные Java-реализации танков, гонок, стрелялки, тетриса; есть также змейка | Упрощённые правила, нет таблицы режимов Apollo; явная лицензия повторного использования не найдена | Отличный материал для понимания устройства игр; прямой перенос кода требует отдельного решения по лицензии |
| **Ранее найденный n0Live/BrickGame** | Более широкая библиотека правил, включая Frogger, достраивающие выстрелы и Pentix | Тоже симулятор, а не ROM Apollo; наборы вариантов не совпадают автоматически | Предпочтительный кандидат для адаптации именно кода: лицензия MIT подтверждена |

**Вывод:** vitalibo действительно даёт логику «Танков», но не пять оригинальных режимов. brick.game может помочь с визуальной проверкой, однако сейчас доказательств, что его внутренний код доступен для переноса или основан на vitalibo, нет. Источники: [README vitalibo][V-Readme], [его игровой каталог][V-GameDir], [сайт][B-Site], [MIT n0Live][N-License].

### Что проверено и что не проверено

Проведён статический разбор файлов vitalibo: запуска и меню, четырёх файлов каталога `game/tanks` (`TanksGame`, `Tank`, `Battlefield`, `Shot`; `Direction.java` отдельно не читался), а также `Point`, `Shape`, `CanvasTranslator`, `RaceGame`, `Car`, `ShootGame`, `Army`, `TetrisGame`, `Board`, `Game`, `Controller`, `Kernel`, README и Maven-конфигурации. Наличие остальных перечисленных каталогов подтверждено деревом репозитория; для змейки выполнена только проверка наличия, без детального анализа правил.

Версия vitalibo зафиксирована: **`f8dd8f0a00954dfc5f6f5752b661082495f8fe78`**. Ссылки на его код в этом документе привязаны к этой версии, а не к изменяемому `master`. [Дерево версии][V-Tree]

Приложение Java не собиралось и не запускалось; его тесты не выполнялись. Для brick.game не получены исходные JavaScript-модули и не выполнен игровой прогон. Нельзя считать приведённые интервалы измеренными на реальном Apollo либо в работающем приложении: это значения из кода донора.

## 2. Самая важная находка: «9999» не означает тысячи реализованных вариантов

В [Run.java][V-Run] зарегистрированы всего пять классов: Snake, Race, Tetris, Shoot, Tanks. В [Menu.java][V-Menu] номер выбирает класс по **остатку от деления на длину этого списка**. Значение меню циклически меняется от 0 до 9999; отдельной таблицы тысяч правил здесь нет.

Есть и расхождение README с кодом: README нумерует игры `0001…0005`, но фактическое индексирование в проверенной версии начинается с нуля.

| Остаток номера при делении на 5 | Класс, который выбирает код | Примеры отображаемого номера |
|---|---|---|
| 0 | `SnakeGame` | 0000, 0005, 0010 |
| 1 | `RaceGame` | 0001, 0006, 0011 |
| 2 | `TetrisGame` | 0002, 0007, 0012 |
| 3 | `ShootGame` | 0003, 0008, 0013 |
| 4 | `TanksGame` | 0004, 0009, 0014 |

Это вывод из статического кода, не из запуска. **Для будущей ручной проверки танки следует искать прежде всего под 0004, а не слепо по 0005 из README.**

Три числа, которые нельзя смешивать:

- пять разных классов игр в vitalibo;
- пять танков суммарно на поле vitalibo в обычном состоянии: игрок и четыре врага;
- пять вариантов танковой игры, которые пользователь наблюдал в меню Apollo.

Ни первые, ни вторые «пять» не объясняют пять вариантов Apollo. Также этот репозиторий **не раскрывает 51 вариант тетриса** и не даёт оснований искусственно доводить сумму вариантов до 168.

| [game/tanks/Battlefield.java][V-Battlefield] | `testDoStep`, `hasOverlap`, `spawn`, `Spawn` | Проверки движения, особый разворот, стартовые позиции и занятость места появления |

### 3.1. Координаты — критическая ловушка

`Point` объявляет сначала `y`, затем `x`; фабрика, генерируемая Lombok, принимает **`Point.of(y, x)`**, не привычные `x, y`. Ось `y` направлена вниз. Поле — **20 строк × 10 столбцов**. [Point][V-Point], [CanvasTranslator][V-Canvas]

В новой TypeScript-реализации лучше применять именованные `{ x, y }`. При переводе описаний стартовых позиций проверять порядок отдельно; не копировать пары чисел без расшифровки.

Танк имеет рамку 3 × 3, а его `point` служит началом этой рамки. Для полностью помещающегося танка допустимы `x = 0…7`, `y = 0…17`. Это границы начала рамки, а не центра. [Tank.verify][V-Tank]

### 3.2. Формы и столкновения

У игрока и врагов в vitalibo используется один каталог четырёх направленных форм. Силуэт при направлении вверх:

```text
010
111
101
```

Здесь `1` — активная клетка. Это **форма vitalibo**, не подтверждённый рисунок Apollo. Для остальных направлений в `Tank.STATES` есть отдельные маски. [Tank][V-Tank]

Принципиально различаются четыре проверки:

| Проверка | Что делает vitalibo |
|---|---|
| Граница экрана | Проверяет рамку танка 3 × 3 |
| Попадание пули | Проверяет совпадение с активной клеткой силуэта |
| Возможность движения | Проверяет пересечение активных клеток танков |
| Появление нового врага | Использует отдельную полную маску 3 × 3 существующих танков и силуэт кандидата |

Последняя строка означает именно алгоритм проверки, а не универсальное утверждение «никакие две рамки никогда не пересекаются». Не заменять все эти случаи одним прямоугольным `boundingBox`: изменится поведение в пустых углах силуэта. [Tank.hasKilled][V-Tank], [Battlefield][V-Battlefield]

### 3.3. Управление

Когда команда совпадает с текущим направлением танка, он перемещается на одну клетку. Когда направление меняется, сначала изменяется форма и ориентация **без перемещения начала рамки**. Следующая команда в этом направлении уже двигает танк. [Tank.doStep][V-Tank]

В `Battlefield.testDoStep` есть исключение: если первая проба пересекается с другим танком и команда направлена строго назад относительно прежнего курса, проверяется результат ещё одного вызова шага. В таком случае два вызова могут означать **разворот и один шаг**, а не перемещение на две клетки. Это специфическое правило донора; не переносить его в Apollo без проверки. [Battlefield.testDoStep][V-Battlefield]

`Space` вызывает `doRotate`, но в танковой игре этот метод означает **выстрел**, а не поворот. Название общего метода не следует переносить в смысл игровых действий нового ядра. [Controller][V-Controller], [TanksGame.doRotate][V-Tanks]

Ввод поступает через Java `keyPressed`. Отдельная внутренняя схема повторов удерживаемого направления в `TanksGame` не задана: скорость ручного управления нельзя выводить из интервала AI. В CrocodileMario использовать уже существующие `pressed/held/released` и явные интервалы повтора, независимые от автоповтора клавиатуры ОС. [Controller][V-Controller], [архитектура проекта][C-Architecture]

### 3.4. Начальное поле и появление врагов

При инициализации создаётся игрок в **`x=4, y=9`** и четыре противника с началами рамок в углах:

| Враг | x | y |
|---|---:|---:|
| Верхний левый | 0 | 0 |
| Верхний правый | 7 | 0 |
| Нижний левый | 0 | 17 |
| Нижний правый | 7 | 17 |

Начальные направления выбираются случайно. Это состояние, создаваемое `init`, а не обещание, что первый увиденный кадр сохранит его: задания таймера запускаются с нулевой начальной задержкой. [Battlefield.Spawn][V-Battlefield], [Kernel.Job][V-Kernel]

На каждом такте AI обрабатываются существующие враги. Если общее число танков после этого меньше пяти, делается попытка добавить **одного** врага. На поиск подходящего места у `spawn` есть до четырёх попыток; случайный выбор может повторно указать тот же угол. Это не гарантированный перебор всех четырёх углов. [TanksGame.Physics.tanksMove][V-Tanks], [Battlefield.spawn][V-Battlefield]

### 3.5. AI

Каждая попытка выбора действия имеет такое распределение:

| Выбор | Вероятность при одной попытке |
|---|---:|
| Попытаться действовать в случайном направлении | 25% |
| Продолжить действовать в текущем направлении | 50% |
| Выстрелить | 25% |

Если выбранное движение невозможно, AI повторяет выбор, максимум до пяти попыток, останавливаясь при первом успешном действии. **Это не итоговые вероятности наблюдаемых действий**: около других танков отказы движения меняют фактическое распределение. [ArtificialIntelligence][V-Tanks]

Здесь нет поиска пути к игроку, проверки линии огня на игрока, защиты базы или тактического обхода стен. Это компактный случайный AI. Не добавлять A* или прицельное преследование только потому, что они кажутся «лучше»: целью является поведение оригинала, а не повышение сложности.

### 3.6. Временные интервалы

Все числа — из кода vitalibo, **не параметры Apollo**.

| Подсистема | Интервал | При speed=1 | При speed=15 |
|---|---|---:|---:|
| AI танков / попытка пополнения | `1000 − 45 × speed` мс | 955 мс | 325 мс |
| Шаг всех танковых снарядов | 150 мс | 150 мс | 150 мс |

Интервал для ручного движения сюда не входит. Настройка `level` в проверенном `TanksGame` не используется для построения карты или выбора варианта. [TanksGame][V-Tanks]

Для демонстрационного профиля допустимо зафиксировать эти значения как `donor-code`. Для профиля оригинала их следует заменить результатами видеоизмерений, сохранив происхождение каждого параметра.

### 3.7. Выстрел, попадание, счёт

Пуля создаётся в клетке дула, вычисленной из начала рамки и направления. На очередном такте снаряды сначала сдвигаются на клетку, затем проверяются попадания. Пули игрока и врагов хранятся в разных списках. [Tank.doShot][V-Tank], [Shot.run][V-Shot], [Physics.bulletFlight][V-Tanks]

При обнаружении поражённых противников удаляются танки и соответствующие пули игрока; счёт увеличивается на **100 за запись об уничтоженном противнике**. Попадание в игрока вызывает общую процедуру `crash`, которая уменьшает счётчик жизней. Поведение полного жизненного цикла и его совпадение с Apollo здесь не подтверждены. [TanksGame][V-Tanks], [Game.crash][V-Game]

В проверенной танковой реализации нет обработки стен, базы, взаимного уничтожения снарядов, урона врагам от вражеских снарядов, отдельного лимита выстрелов игрока или cooldown его пушки. Это **отсутствующие механики донора**, а не подтверждённое отсутствие этих правил в Apollo.

### 3.8. Чего в этом источнике нет для пяти режимов Apollo

Нет карт препятствий и разрушаемых стен, целей защиты базы, пяти самостоятельных конфигураций режима, таблицы уровней или завершения волн с заданным числом убийств. В таком виде источник лучше всего описывает **бой на пустом поле с пополнением врагов**. [TanksGame][V-Tanks], [Battlefield][V-Battlefield]

Нельзя автоматически назвать эту реализацию режимом №1 Apollo. Пока это только кандидат для сравнения с каждым из пяти режимов.

## 4. Остальные игры: что можно получить

### 4.1. Гонки

Читать [RaceGame.java][V-Race] и [Car.java][V-Car]. Это реализованные двухполосные гонки, без стрельбы.

| Правило vitalibo | Что видно в коде |
|---|---|
| Перестроение | Сдвиг на три столбца между двумя положениями |
| Игрок | Автомобиль с клеточным силуэтом 3 × 4 внизу экрана |
| Соперники | Генерируются в одном из двух положений и движутся вниз |
| Ритм | `300 − 18 × speed` мс на дорожный шаг: 282 мс при speed=1, 30 мс при speed=15 |
| Появление машины | Каждые девять шагов дорожного счётчика; список ограничивается тремя машинами |
| Очки | +10 за вызов дорожного шага, а не только за обгон |
| UP и Space | Вызывают дополнительный дорожный шаг; **не стреляют** |
| Жизни | В конструкторе выставляются три |
| Прогресс | При дорожном счётчике от 1000 увеличивается скорость и переинициализируется игровая сцена |

Перестроение проверяет столкновение в итоговой позиции; промежуточные столбцы отдельной анимацией движения здесь не симулируются. Сопоставить это с Apollo, прежде чем добавлять плавный переход или промежуточные коллизии. [Car][V-Car], [RaceGame][V-Race]

**Для `racing-shooting` это только транспортная часть.** Нельзя объявить готовую стреляющую гонку на основании присутствия пуль в другой игре репозитория. Доступность оружия, траектория, уничтожаемые цели и условия поражения требуют отдельного профиля.

### 4.2. Стрелялка Shoot

Читать [ShootGame.java][V-Shoot] и [Army.java][V-Army]. Снизу игрок стреляет вверх по потоку клеток, который пополняется сверху.

Каждый шаг атаки сдвигает все существующие клетки на строку вниз и случайно добавляет клетки в верхнюю строку: для каждого из десяти столбцов вызывается `nextBoolean`. Бокового движения массива и самостоятельно отделяющихся «мух» здесь нет. Выход хотя бы одной клетки ниже строки 19 вызывает поражение. [Army][V-Army]

| Параметр vitalibo | Значение |
|---|---|
| Шаг атаки | `1000 − 40 × speed` мс |
| Шаг пули | 25 мс |
| Начальные жизни | 3 |
| LEFT / RIGHT | Сдвиг пушки |
| UP / Space | Выстрел |
| DOWN | Пустой обработчик |

Точные границы движения пушки и её начальную координату следует проверить в `Gun.java` перед адаптацией: этот файл здесь отдельно не анализировался. [ShootGame][V-Shoot]

**Важное отличие от пункта 5 Apollo:** «общий массив и отдельные точки-враги» не равно случайно пополняемым рядам. Shoot даёт полезную примитивную механику «пуля — клетка», но не всю наблюдаемую игру. Он также не реализует достройку отдельной фигуры или строительные выстрелы.

### 4.3. Тетрис

Читать [TetrisGame.java][V-Tetris], [Board.java][V-TetrisBoard] и [каталог фигур][V-TetrisDir]. В каталоге есть семь классов обычных тетромино: I, J, L, O, S, T, Z. Каталога Pentix и 51 варианта Apollo здесь не найдено.

У проверенного ядра есть текущая и следующая фигуры, попытки сдвига/поворота с проверкой пересечения, фиксация фигуры и очистка строк. Интервал автоматического падения — `700 − 40 × speed` мс. В `Board.init(level)` уровень задаёт число нижних рядов, изначально заполненных случайными клетками. [TetrisGame][V-Tetris], [Board][V-TetrisBoard]

Начисление очков линейное: **100 за удалённую строку**. Оно не совпадает ни с таблицей на упаковке Crocodile Mario, ни автоматически с правилами Apollo «168 в 1». Не заменять существующий тетрис CrocodileMario этой реализацией ради одного названия: это не даёт недостающих вариантов и добавляет работу по повторной интеграции.

### 4.4. Змейка и непокрытые игры

Змейка зарегистрирована в `Run.java`, присутствует в README и игровом каталоге; её детальные правила здесь не разбирались. В девяти играх Apollo из списка пользователя её нет, поэтому добавлять её на эту консоль не требуется. [Run][V-Run], [README][V-Readme]

Frogger, Pentix, гонки со стрельбой, достройка отдельных фигур, строитель, арканоид и морской бой среди пяти зарегистрированных игр vitalibo отсутствуют. Наличие игры с похожим названием на brick.game не восполняет отсутствие её исходников в vitalibo.

## 5. Ловушки донора, которые надо учесть в тестах

Это статические наблюдения и риски переноса; они не являются отчётом о воспроизведённых сбоях Java-приложения.

| Место | Наблюдение | Действие в новой реализации |
|---|---|---|
| `Point.of` | Порядок `y, x` | Использовать именованные координаты; тестировать несимметричные позиции |
| `TanksGame.init` | В существующие коллекции танков добавляются новые; списки снарядов не очищаются внутри `init`. `Controller.reinit` вызывает `init` того же объекта | Перезапуск строит новое чистое состояние; отдельный тест на повторный старт |
| `ShootGame.doShoot` + `Army.killEnemy` | Удаляться могут несколько клеток, но метод возвращает только boolean; +10 начисляется один раз за такт с хотя бы одним попаданием | Не выдавать это за «10 за врага». Проверить оригинальное начисление отдельно |
| `ShootGame` | Не видно удаления промахнувшихся снарядов при уходе выше экрана; рендерер просто игнорирует внеэкранные точки | Явно удалять завершённые снаряды; стресс-тест длительной стрельбы |
| `Controller.keyPressed` | События сразу вызывают движение/выстрел | В новом ядре задавать частоты через такты, а не ОС |
| `Kernel.Job` | Имя берётся из класса объекта; разные строковые метки получают одно имя класса `String` | Не переносить этот реестр заданий; использовать стабильные явные идентификаторы |
| `CanvasTranslator` | Итоговая boolean-матрица объединяет разные сущности и пропускает внеэкранные точки | Матрица — только изображение; владение пулями, урон и сущности хранятся отдельно |
| `TanksGame.init` | Счёт обнуляется при вызове `init` | Разделить новую партию, новый уровень и восстановление после потери жизни |

Источники: [TanksGame][V-Tanks], [ShootGame][V-Shoot], [Army][V-Army], [Controller][V-Controller], [Kernel][V-Kernel], [CanvasTranslator][V-Canvas]. Не следует называть особенности счёта или столкновений «ошибками оригинала»: оригинал в этой проверке не запускался.

## 6. Что именно даёт brick.game

В публичном каталоге заявлены 13 игр: танки, гонки, змейка, арканоид, бомбер, диггер, понг, тетрис и пять названных вариантов тетриса. Текст про танки упоминает защиту базы. Игры вроде бомбера, диггера и понга не надо добавлять в набор Apollo, если они не подтверждены оригинальным меню. Встречающиеся на сайте названия вариантов тетриса также не задают соответствие конкретным номерам 1–51.

Полезный следующий этап для разработчика с работающим браузером — интерактивно сравнить поворот танка, форму спрайта, число противников, стены/базу и выстрел. Наблюдения подписывать **«поведение brick.game»**, не «оригинал».

### Проверка JavaScript, которая пока не выполнена

В обычном DevTools на открытой странице можно получить список подключённых скриптов, не угадывая названия файлов:

```js

```

После запуска нужной игры проверить также Network: код может загружаться позже или находиться во вложенном frame. В Sources искать фактические функции движения, генерации противников, проверки попадания и таблицы фигур. Проверенные условия использования сайта не предоставляют явной открытой лицензии на перенос его кода. Пока использовать сайт как референс, а вопрос повторного использования конкретных модулей решать после установления их происхождения и лицензии. [Условия сайта][B-Terms]

## 9. Как внедрять в актуальный CrocodileMario без двойной работы

### 9.1. Что в проекте уже есть

В проверенном [src/games/catalog.ts][C-Catalog] **уже существуют** все девять подходящих идентификаторов из таблицы выше. Не создавать параллельные `tanks`, `frogger`, `builder`, `pentris`: это будут дубли имеющихся `tank`, `frog`, `construction`, `tetris-pentix`.

Каталог пока допускает движки `mario` и `tetris`; танки и другие ещё не восстановленные игры имеют `engine: null`. В [src/app/toys.ts][C-Toys] уже хранится порядок игр `tank168`, а у танков записаны пять вариантов. Сама запись в каталоге не означает, что игра подключена к оболочке.

[Архитектура][C-Architecture] уже отделяет ядро от браузера, имеет фиксированный шаг, кадры ввода, seed/replay, жизненный цикл приложения и LCD-рендерер тетрис-подобных игрушек. Это следует сохранить, а не заменять Swing-приложением внутри браузера.

### 9.2. Предлагаемый минимальный план

**Этап 1 — отдельное чистое ядро танков.** Новая партия создаёт новое состояние: игрок, противники, пули, счёт, фаза, состояние ГСЧ и временные накопители. Сначала реализовать один явно обозначенный приближённый профиль. Не утверждать, что это уже оригинальный режим №1.

**Этап 2 — подключение выбранной игры к существующей оболочке.** Расширить реестр запуска так, чтобы реально выбранный `GameId` определял модуль, а не все пункты `tank168` продолжали запускать тетрис. Название будущего общего grid-runtime — проектное решение, не уже существующий API.

**Этап 3 — общий формат изображения матричных игр.** Матрица 10 × 20 и независимые поля HUD/мигания должны поступать в LCD-рендерер через адаптер. `render/tetrisScreen.ts` сейчас относится к тетрису: нельзя просто подать туда состояние танков без проверки контракта. Если нужен рефакторинг, вынести рисование клеток отдельно от тетрис-специфичных данных NEXT.

**Этап 4 — гонки и простая стрельба.** После второй игры выделить действительно общие операции: клеточные маски, пересечения, границы, идентификаторы объектов, детерминированные интервалы. Не создавать заранее сложный универсальный движок для всех жанров и не писать новый input/audio/lifecycle для каждой игры.

**Этап 5 — профили Apollo.** Настройки разделять по устройству, игре и варианту. Одинаковый `GameId` у «Морского боя» и «168 в 1» не гарантирует одинаковые числа врагов, уровни или правила. Непроверенные настройки остаются временными данными, а не неявными константами.

### 9.3. Два разных вида статуса

Нынешний `GameStatus` (`ready`, `placeholder`, `planned`) отвечает за доступность игры. Он не должен подменять достоверность отдельного правила.

Для правила дополнительно хранить происхождение, например:

| Поле | Пример |
|---|---|
| `value` | 150 |
| `unit` | ms |
| `evidence` | donor-code |
| `source` | vitalibo `TanksGame.java`, зафиксированный commit |
| `originalVerified` | false |

Это **предлагаемый формат**, не требование переименовывать существующие схемы. Его задача — не дать интервалу из Java-симулятора превратиться в «измерение Apollo». Отдельно различать сведения со слов пользователя, наблюдение видео оригинала и рабочую гипотезу.

### 9.4. Ограничения игрового ядра

Не переносить Java `Timer`, Swing, `CopyOnWriteArrayList`, UUID и несохранённые случайные генераторы в новую симуляцию. Использовать стабильные числовые ID и воспроизводимый ГСЧ; состояние случайности и временные остатки должны входить в сохранение/replay.

Порядок одновременных событий задать явно: ввод, движения, появление, полёт, попадания, смена фазы. Конкретный порядок — отдельное правило профиля, а не следствие случайного порядка таймеров браузера. Одно поражение игрока не должно списывать несколько жизней из-за нескольких попаданий в одном такте.

25-миллисекундную пулю стрелялки нельзя незаметно округлить до 50 мс только потому, что у другого ядра 20 тактов/с. Нужны подходящая частота матричного ядра или детерминированная обработка подшагов/сроков событий. При более длинном такте проверять все пройденные клетки, а не телепортировать пулю сразу в конечную.

Новое ядро включить в проверки границ `tsconfig.core.json` и ESLint. Правило «без DOM, часов, сети и Math.random» должно реально проверяться для новых файлов, а не оставаться только в документации. [Текущие ограничения проекта][C-Architecture]

## 10. Приёмочные тесты

Следующие тесты предлагаются для новой реализации; это не список уже выполненных проверок.

| Группа | Проверка |
|---|---|
| Геометрия | Начало рамки в `x=4, y=9` не превращается в `x=9, y=4`; все четыре ориентации имеют корректные клетки |
| Управление | Смена направления и последующее движение разделены согласно выбранному профилю |
| Граница | Танк не выходит за допустимые границы рамкой; крайняя пуля корректно удаляется |
| Поворот рядом с танком | Отдельно проверить особый разворот донора; не включать его в Apollo без основания |
| Маски | Пуля в пустом углу силуэта отличается от пули в активной клетке, если именно такой hitbox выбран |
| Появление | Новый враг не нарушает правило занятости; заблокированные точки не вызывают бесконечный поиск |
| AI | Число попыток ограничено; одинаковый seed даёт одинаковую последовательность действий |
| Счёт / жизнь | Несколько попаданий обрабатываются по заданному правилу; смерть фиксируется один раз на фазу |
| Перезапуск | Повторный старт не сохраняет старые танки, пули, счёт и таймеры |
| Долгая стрельба | Число завершённых внеэкранных пуль не растёт без ограничения |
| Скорость | Интервалы проверяются как время симуляции, не количество отрисованных кадров |
| Детерминизм | Одна и та же записанная последовательность ввода даёт одинаковые состояния при 30/60/144 FPS отображения |
| Пауза / переключение | Возврат из паузы не вызывает скачок; уход на другую игрушку прекращает её симуляцию и звук |
| Меню | Выбор танков запускает танки; неподдержанные варианты не маскируются пятью одинаковыми «готовыми» режимами |

Для происхождения значений в fixture указывать профиль, версию правил и источник. Тест на модель донора не является доказательством соответствия оригиналу.

## 11. Что ещё надо увидеть на оригинальной Apollo

Для каждого из пяти танковых вариантов достаточно начать с короткого одинакового протокола: номер режима, старт без действий, одиночные нажатия направлений, удержание, одиночный и длительный огонь, столкновение/поражение. Затем отдельно проверить стены и переходы уровней, если они присутствуют.

| Неизвестное | Какое наблюдение нужно |
|---|---|
| Различия пяти вариантов | Пять стартовых экранов и короткие игровые эпизоды каждого, а не один общий скриншот |
| Число и появление врагов | Старт, уничтожение одного врага, появление замены |
| Стены / база | Попадание в каждый тип препятствия; условие конца партии |
| Поворот | Два одиночных нажатия нового направления, затем удержание |
| Лимит и ритм стрельбы | Удержание кнопки на пустой линии огня |
| Коллизия пуль | Встречные выстрелы, если это удаётся воспроизвести |
| Продолжение после смерти | Сохраняются ли враги, карта, счёт и номер уровня |
| Тетрис 1–51 | Номер + наблюдаемое правило; не вычислять варианты из числа на наклейке |
| Достройка / строитель | Исчезает отдельный прямоугольник, полная строка или другой объект |

Не требуется откладывать всю разработку до получения всех ответов: общий каркас можно сделать сейчас, а неизвестное держать явно выделенными параметрами и неподтверждёнными профилями.
